## Pipeline

```text
#[randomize] / #[constraints]           (compile time)
  -> code that builds the constraint IR
randomize()                             (run time)
  1. pre_randomize (the object's, then its random nested objects')
  2. if there are random `Vec`s: build the IR in the size phase and
     solve it for the lengths
  3. build the IR with the lengths fixed: variables for the random
     fields, constants for the state + the type's constraints + the
     attached sets + per-call constraints
  4. solve in stages
  5. on success: write back, commit the object's generator,
     post_randomize; on failure: return RandError, nothing changed
```

The code lives in `crates/rustdv-veryl/src/random/`:

| File | Contents |
|---|---|
| `mod.rs` | the public API, `RandState`, `RandField`, the driver (`run`) |
| `builder.rs` | `Builder`: the API the generated code calls; `Operand` |
| `ir.rs` | typed expressions, typing rules, constant folding, the evaluator |
| `blast.rs` | bit-blasting to CNF |
| `sat.rs` | the `SatSolver` trait and the batsat implementation |
| `solve.rs` | the staged solver |
| `rng.rs` | SplitMix64 |
| `tests.rs` | the differential test |

The macros are in `crates/rustdv-veryl-macros/src/random.rs`.

## Macros

- **`#[randomize]`** adds the hidden state field `__rand_state`
  (`RandState<Self>`: the object's generator, the on/off flags, the
  attached constraint sets, *later* the `randc` history) and generates:
  - the name constants of the random fields (`AluCmd::A`),
  - `RandStruct`: the field names (`FIELDS`, used by the other macros
    for compile-time checks), and functions that declare the fields as
    an `Operand`, write a solution back and call the hooks,
  - `RandField`, so the struct can be a nested field,
  - inherent methods forwarding to `Randomize`, so calling them needs no
    import.

  A state field may have any type. Whether it can be used in
  constraints is decided by autoref specialization on its concrete type
  (`(&Probe(&x)).declare_state(..)` picks `ViaField` for a `RandField`,
  `ViaOther` otherwise); using an unusable one is an `Invalid` error.
  Whether the type has `#[constraints]` is found the same way
  (`TcProbe`), so a struct needs no constraint block.
- **`#[constraints]`** sees only the impl block, not the struct
  definition. It checks that each single identifier in a body is a field
  by a `const` assertion against the field list generated by
  `#[randomize]` (`has_field`, a `const fn`), so typos are compile
  errors. It generates, per block, a name constant and a closure that
  builds that block's IR, run through `Builder::block`, which skips
  blocks turned off or replaced. The impl becomes `TypeConstraints`, so
  there can be only one `#[constraints] impl` per type. Every constraint
  item records its block (or set) name, source location (`file!()` and
  `line!()` at the statement's span) and text, for the unsat report.
- **Code generation:** each constraint expression becomes Rust code that
  makes an `Operand` (a scalar `Expr`, an array, a `Vec` or a struct)
  through `Builder` methods, with every sub-expression bound to a
  temporary first (the builder is borrowed mutably by each call). An
  `if` on a constant condition builds only the taken branch, which is
  what lets a guard like `if i + 1 < v.len()` prevent an out-of-range
  index.
- **`#[constraints(for T)]`** does the same for a constraint set and
  implements `Constraints<T>` for it. Attached sets are held as
  `ConstraintSet<T>` (`Arc<dyn Constraints<T>>`), so the object's type
  does not change and `clone()` shares them.
- **`#[constraint_fn]`** cannot be expanded in the caller's tokens: a
  proc macro cannot read the body of a function defined elsewhere.
  Instead it generates an ordinary function that takes the arguments as
  IR and returns IR, and the expansion happens when the IR is built.
  Because the parameters are IR, not Rust values, a `{ expr }` inside the
  body cannot use them (compile error). Direct recursion is detected by
  the macro; mutual recursion by a depth limit while building the IR.

## Arrays

`Vec<T>` is solved in two steps, as SV §18.5.8.1 orders it:

1. **Size:** the constraints on `v.len()` are solved alone. The vector is
   then truncated or extended (new elements from `T::default()`).
   A `Vec` without an upper bound on its length is an error, instead of
   unrolling without limit.
2. **Elements:** each element becomes a separate variable (`v_0`, `v_1`,
   ...; for a struct element `v_0.a`, `v_0.b`, ...). Loops over the array
   are unrolled with constant indices; a condition on the loop index
   (`if i + 1 < v.len()`) is folded during unrolling. All element
   variables are solved together as one problem with the rest of the
   object. A constant index outside the array is an error.

An index that is itself random (`v[idx] == 3`) is expanded into one case
per element: `(idx == 0 -> v_0 == 3) && (idx == 1 -> v_1 == 3) && ...`.

Elements whose constraints refer only to themselves may be split into
independent sub-problems (see [staged solver](#staged-solver)).

Multi-dimensional arrays are not supported. If added, only fixed-size
ones (`[[T; M]; N]`), which flatten the same way; nested variable sizes
(`Vec<Vec<T>>`) would need sizes solved per row and are out of scope.

## Seeds

- The module keeps a seed source per thread. rustdv does not expose the
  current test's seed outside its context, so a test seeds the source
  with `random::set_seed(ctx.seed())`; unseeded, it starts from
  `RUSTDV_RANDOM_SEED` (or 1). Seeding it automatically per test needs a
  hook in rustdv's runner.
- An object takes a seed from it on its first `randomize()` and keeps its
  own generator in the hidden field (random stability).
- `randomize()` takes no RNG argument because rustdv's `rng()` of a
  component or sequence builds a new generator from the same seed on
  every call; passing it to each `randomize()` would start every call
  from the same sequence.

## IR caching

The first implementation rebuilds the IR and the CNF on every
`randomize()`. Caching the structure of the IR per type (inserting only
the values of state fields and constants), and reusing the CNF across
calls (by passing constants as assumptions instead of folding them),
are decided later from measurements.

## Staged solver

Solving is a sequence of stages over one incremental SAT instance;
each stage adds assumptions to those of the stages before it:

1. **Unconstrained variables** (used by no constraint) are picked
   directly, without SAT: a random variant for an enum, random bits
   otherwise.
2. **Hard constraints:** each top-level item gets a selector literal
   (`!sel | !guard | item`), and the instance is solved with all
   selectors assumed. On UNSAT, the selectors in the unsat core name the
   conflicting items for the report. Items under an `if` are guarded by
   its condition.
3. **`Vec` lengths** (size phase only): a length that may exceed 65536
   under the constraints is an `Invalid` error.
4. **`soft`:** highest priority first (later blocks), each soft item's
   selector is added if the instance stays satisfiable.
5. **`solve_before`:** the variables are fixed in order, each to a
   random value checked under assumptions (8 tries), else to its value
   in a model.
6. **`dist`:** a range is picked by its weight and a value in it, and
   assumed if it fits (8 tries); otherwise the value is left to the
   solver.
7. **The rest:** the final model. Every bit of a random variable gets a
   random preferred polarity (batsat's user polarity) from the object's
   generator, which spreads the solutions; uniformity is not guaranteed.

Planned refinements: a domain analysis (intervals and value sets from
`inside` and comparisons with constants) so that more variables are
picked without SAT, and splitting `Vec` elements whose constraints refer
only to themselves into independent sub-problems.

### Bit-blasting

Each expression is encoded with Tseitin gates at the widths its type
gives (operands sign- or zero-extended first), with constant folding on
literals. Notes:

- `/` and `%` add a side condition (divisor non-zero) to the item that
  contains them; a side condition inside a branch of a value `if` holds
  only when that branch is taken, matching the evaluator.
- Unsigned division by a constant power of two is a shift or a mask;
  other divisions use a restoring divider, signed ones on magnitudes.
- Comparisons extend both operands to a common signed width when either
  is signed, so values compare as integers.

The differential test (`random/tests.rs`) checks the circuit against the
evaluator on random expressions of random types.

`randc` (*later*) is added as a stage before stage 4: pick an unused
value from the history, check it with SAT under assumptions, and record
it only when the whole `randomize()` succeeds.

## State changes are transactional

All state that `randomize()` changes (field values, the object's
generator, *later* the `randc` history) is kept in a scratch copy during
the call and committed only on success.

## SAT solver

- batsat 0.6 (MIT; a Rust port of MiniSat 2.2) is the default.
- The bit-blaster and the stages use only a `SatSolver` trait:

  ```rust
  trait SatSolver {
      fn new_var(&mut self) -> Var;
      fn add_clause(&mut self, lits: &[Lit]);
      fn solve(&mut self, assumptions: &[Lit]) -> SolveResult; // Sat / Unsat / Interrupted
      fn value(&self, var: Var) -> bool;
      fn unsat_core(&self) -> &[Lit];
      fn set_stop(&mut self, stop: Arc<AtomicBool>);
  }
  ```

- The batsat implementation is behind a default cargo feature, so
  another solver can be plugged in.
- varisat (cannot be interrupted) and OxiZ 0.3.3 (wrong answers) were
  evaluated before and rejected.

## Testing

- Differential tests: the bit-blasted circuit against an evaluator of
  the IR, on random constraints and random values.
- Unsatisfiable constraints: error reporting and atomicity.
- Porting the constraints of tvip-axi as a realistic workload.

## Deferred items

- `randc`
- multi-dimensional arrays (fixed-size only, if ever)
- signed values wider than 128 bits
- `randsequence`
- caching the IR per type, and reusing the CNF across calls
- the domain analysis stage, and splitting independent `Vec` elements
- seeding the per-thread source automatically per test (needs a rustdv
  runner hook)
- generic `#[randomize]` structs; a random index into an array of structs
- a `sequential` mode for very large arrays (see the decisions below)

## Differences from SV

Exact SV rules are kept only where they are cheap:

- **Widths (§11.6):** SV re-sizes operands from the surrounding context
  and lets results wrap. That propagation is the costly part; instead,
  `+`, `-`, `*` are overflow-free, with widths decided bottom-up (`+`/`-`:
  the wider operand plus one bit, `*`: the sum of the widths). Literals
  take their smallest width, not 32 bits. Comparisons are on values,
  regardless of signedness.
- **Functions (§18.5.12):** SV lets a plain function take random
  arguments by solving them first, which needs the problem split into
  ordered parts. Here plain functions run only inside `{ }`, as
  constants; `#[constraint_fn]` functions are expanded, so their
  arguments are solved together with the rest (stronger than SV).
- **Out-of-range constant index:** an error, instead of a constraint
  that is silently not generated.
- **Uniformity** over the whole solution space is not guaranteed.

## Decisions and rejected alternatives

- **Module name `random`:** `rand` would clash with the `rand` crate.
- **Attribute macro, not a derive:** a derive cannot add the hidden
  state field.
- **Constraint bodies in Rust syntax, parsed by the macro:** keeps
  editor support and compile-time name checks, unlike a string DSL.
  Alternatives such as builder APIs read poorly for nested constraints.
- **`bit_not(a)` instead of `~a`:** Rust has no `~` operator, and the
  body of an attribute macro is parsed by rustc first, so `~a` is
  rejected before the macro sees it. Function-like macros
  (`constraints! { ... }`) would accept `~`, but rustfmt and
  rust-analyzer would no longer work inside constraint blocks; the
  bitwise complement is rare in constraints, so that was not worth it.
- **Arrays are flattened after the size is fixed**, rather than solving
  element by element with earlier elements fixed as constants. The
  sequential approach fails on satisfiable problems (e.g. a strictly
  increasing `u8` array after choosing 250 for the first element) and
  skews the distribution like an implicit `solve_before`. A `sequential`
  opt-in for very large arrays may be added later, with a feasibility
  check per element.
- **Variations by constraint sets, not inheritance:** most SV `extends`
  only adds or replaces constraints. An `inherit` attribute with `Deref`
  to the base was considered and rejected: `Deref` for inheritance is
  unidiomatic, and the macro cannot see the base's fields. New fields
  are added by embedding the item as a nested object; no dedicated
  feature (such as `#[replaces(base.x)]`) is provided for it, since
  `constraint_off` covers that rare case.
- **No runtime constraint override:** a registry that replaces a
  constraint of every object of a type (like the UVM factory type
  override) was dropped. Its use case, changing the constraints of
  items made inside a sequence the test does not own, depends on the
  sequence's implementation details. What a sequence lets a test vary
  is part of the sequence's interface: its own parameters (such as a
  `ConstraintSet<T>` it applies to its items), or replacing the
  sequence as a whole.
- **Lightweight semantics over SV conformance:** exact SV rules are kept
  only where they are cheap; see [differences from SV](#differences-from-sv).
- **No RNG argument to `randomize()`:** see [seeds](#seeds).
- **`dist` keywords `each`/`total`** instead of `:=`/`:/` for
  readability.
- **On/off by name (`rand_off`, `constraint_off`)** instead of a mode
  argument; `const` is avoided because it is a Rust keyword.
